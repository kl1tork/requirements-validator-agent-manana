# Манана — агент проверки требований

**Манана** — ИИ-агент для статического ревью готового документа требований **до разработки**. Агент разбивает документ на отдельные требования, проверяет каждое из них и весь набор целиком по критериям ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE Std 830-1998 (п. 4.3), а затем записывает отчёт на русском языке.

Решение для кейса BCC-HUB x MNU FinTech Hackathon — «Агент проверки требований». В коде агент живёт в пакете `reqval`, поэтому команды запуска начинаются с `python -m reqval`.

```
python -m reqval input/requirements.pdf reports/report.md
```

## Быстрый старт

### 1. Установка (Python 3.10+)

```bash
git clone <ссылка на этот репозиторий>
cd requirements-validator-agent
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Ключ LLM

Модель по умолчанию — **Google Gemini `gemini-3.5-flash`**. Хватает бесплатного тарифа. Если она перегружена или снята, агент сам переключается на запасные (`gemini-3.6-flash`, затем `gemini-3.8-flash`).

1. Откройте https://aistudio.google.com/apikey и войдите с Google-аккаунтом.
2. Нажмите **Create API key** и скопируйте ключ.
3. Создайте файл `.env` из примера и вставьте в него ключ:

```bash
cp .env.example .env               # Windows: copy .env.example .env
```

```dotenv
LLM_PROVIDER=gemini
GEMINI_API_KEY=ваш_ключ
GEMINI_MODEL=gemini-3.5-flash
# запасные модели через запятую; пустое значение отключает переключение
# GEMINI_FALLBACK_MODELS=gemini-3.6-flash,gemini-3.8-flash
```

Файл `.env` указан в `.gitignore`, поэтому ключ не попадёт в репозиторий. Вместо файла можно задать переменные окружения.

Поддерживаются и другие провайдеры, их выбирают через `LLM_PROVIDER`: `openai` (подходит любой OpenAI-совместимый endpoint, в том числе OpenRouter, Groq, vLLM или LM Studio через `OPENAI_BASE_URL`), `anthropic` и `ollama` (локальная модель, ключ не нужен). Примеры настроек есть в `.env.example`.

### 3. Прогон

Положите выданный организаторами документ, например, в `input/`. Содержимое папки не коммитится. Затем запустите:

```bash
python -m reqval input/requirements.pdf reports/report.md
```

* 1-й аргумент — путь к документу требований: `.pdf`, `.md`, `.txt`, `.docx` или `.html`.
* 2-й аргумент — путь к отчёту. Если его не указать, отчёт запишется в `reports/report.md`. По расширению выбирается формат: `.md`, `.html` или `.json`.

Агент записывает два файла:

| Файл | Что внутри |
| --- | --- |
| `reports/report.md` | отчёт для сдачи (Markdown, русский язык) |
| `reports/report.json` | те же результаты в машиночитаемом виде: требования, замечания, статусы, цитаты |

В консоли отображается ход прогона по 6 этапам. На документ среднего объёма уходит 8–12 запросов к модели. С бесплатным тарифом Gemini прогон занимает 1–3 минуты: агент сам выдерживает паузу между запросами и повторяет их при ответах `429` и `5xx`. Если основная модель отвечает `404` (снята) или трижды подряд `429`/`503` (перегружена), агент до конца прогона переходит на следующую модель из `GEMINI_FALLBACK_MODELS`; в паспорте отчёта это отмечается.

Чтобы получить HTML-отчёт: `python -m reqval input/requirements.pdf reports/report.html`.

Вариант «всё сразу» для macOS/Linux: `bash run.sh [файл требований] [файл отчёта]`. Скрипт создаёт `.venv`, ставит зависимости, создаёт `.env` и открывает его, если ключ ещё не вписан, а затем запускает прогон.

### Опции

```
python -m reqval INPUT [OUTPUT] [--provider gemini|openai|anthropic|ollama] [--model NAME]
                 [--env PATH] [--batch-size 6] [--segmenter llm|rules] [--no-verify] [--no-cache] [-q]
```

* `--model` — переопределяет модель из `.env`, например `--model gemini-pro-latest`.
* `--batch-size` — сколько требований отправлять модели за один запрос. Меньшее значение даёт более подробную проверку ценой большего числа запросов.
* `--segmenter rules` — нарезка без модели, только по структуре документа (резервный режим).
* `--no-verify` — отключает проход перепроверки замечаний.
* `--no-cache` — не использовать кэш ответов. По умолчанию ответы сохраняются в `.cache/`, поэтому повторный прогон того же документа той же моделью воспроизводит тот же отчёт и не расходует квоту.

## Состав отчёта

| Раздел | Содержание |
| --- | --- |
| 1. Паспорт прогона | документ, его SHA-256, дата, модель и провайдер, версия агента (`git describe`: тег или коммит), число запросов |
| 2. Как агент нарезал требования | таблица «ID в отчёте — ID в документе — раздел — место — краткая формулировка — цитата». Пунктам без номера агент присваивает свой `R-NN` и сохраняет цитату |
| 3. Проверка каждого требования | матрица «требование × 10 критериев» и замечания по каждому требованию |
| 4. Проверка всего набора | 8 свойств набора и межразделовые замечания: противоречия (с цитатами из всех конфликтующих мест), пропуски, терминология |
| 5. Сводка | число требований и нарушений, разбивка по серьёзности и критериям; списки непроверяемых, противоречивых и неполных формулировок |
| 6. Итог | можно ли начинать разработку и тестирование (да / условно / нет) и что исправить в первую очередь |
| Приложения | A — отклонённые и неподтверждённые замечания модели; B — сигналы линтера; C — методика |

У **каждого нарушения** есть место в документе: номер строки (для PDF ещё и страница) и дословная цитата.

## Как работает агент

```
документ ─► чтение и нумерация строк ─► линтер ─► нарезка ─► проверка каждого ─► проверка набора ─► перепроверка ─► отчёт
            (PDF/DOCX/MD/TXT/HTML)      (правила)  (LLM+парсер)  (LLM, пакетами)   (LLM)             (LLM)
                                                        ▲               ▲               ▲
                                                        └──── привязка цитат к строкам документа (grounding) ────┘
```

1. **Чтение.** Текст извлекается построчно, каждая строка получает сквозной номер. Таблицы в PDF собираются в строки вида `| ячейка | ячейка |`; для PDF также сохраняется номер страницы. Модель получает документ в виде `L0042| текст`.
2. **Линтер** (`reqval/lint.py`, без модели) находит маркеры дефектов: размытые слова («быстро», «и далее»), заглушки (TBD, прочерки), незаполненные чек-листы. Результаты используются только как подсказки для модели и сами по себе нарушениями не считаются.
3. **Нарезка.** Модель выделяет требования во всех разделах, включая критерии приёмки, шаги логики API, параметры и коды ответов. Парсер контролирует, что ни один пункт с явным идентификатором (`Ф-1`, `FR-2`…) не потерян. Каждая цитата сверяется с текстом документа.
4. **Проверка каждого требования.** Требования отправляются пакетами вместе с полным документом, чтобы модель видела противоречия с другими разделами. Оцениваются 10 свойств: необходимость, уместность (без лишних проектных решений), однозначность, полнота, единичность, выполнимость, проверяемость, корректность, соответствие шаблону и прослеживаемость.
5. **Проверка набора.** Оцениваются полнота, непротиворечивость, выполнимость, понятность, возможность валидации, ранжирование, модифицируемость и прослеживаемость. Модель целенаправленно сверяет функциональные требования с критериями приёмки, диаграммами, требованиями к данным, API и дочерним документом.
6. **Привязка цитат (защита от галлюцинаций).** Цитата из каждого замечания ищется в документе: сначала точно, затем после нормализации (регистр, ё/е, пробелы в числах, markdown, переносы строк PDF), затем нечётко. Номер строки в отчёте всегда берётся из найденной позиции, а не со слов модели. Замечания без найденной цитаты в выводы не попадают и перечислены в приложении A.
7. **Перепроверка.** Отдельный запрос к модели в роли «второго ревьюера» отсеивает ложные срабатывания и дубли, корректирует серьёзность, пишет резюме и список приоритетов.
8. **Итог** определяется детерминированно: есть критичные дефекты — «нет», есть существенные — «условно», иначе — «да».

Для воспроизводимости используются `temperature = 0`, кэш ответов, SHA-256 документа и версия агента в паспорте.

### Структура репозитория

```
reqval/
  cli.py        — командная строка
  pipeline.py   — оркестрация прогона
  document.py   — чтение PDF/DOCX/MD/TXT/HTML, нумерация строк, разделы
  lint.py       — детерминированный линтер формулировок
  segment.py    — нарезка требований (LLM + парсер)
  analyze.py    — проверка требований и набора, перепроверка
  grounding.py  — привязка цитат к строкам документа
  criteria.py   — критерии 29148 / 830
  prompts.py    — промпты
  llm.py        — клиент Gemini / OpenAI / Anthropic / Ollama на стандартной библиотеке, повторы, запасные модели, кэш
  report.py     — отчёт (Markdown / HTML / JSON)
tests/          — автотесты (без обращения к реальной модели)
```

### Тесты

```bash
python -m unittest discover -s tests -v
```

В тестах вместо реальной модели используется подставная, поэтому ключ не нужен. Проверяются чтение форматов, привязка цитат, отбрасывание «выдуманных» замечаний и требований, добавление пропущенных моделью пунктов, перепроверка и структура отчёта.

## Что сдать

1. Ссылку на этот репозиторий.
2. Выданный документ требований.
3. Отчёт `reports/report.md`, сгенерированный командой выше. Используемая модель и версия агента указаны в его паспорте.

Перед прогоном, который пойдёт в сдачу, закоммитьте код и поставьте тег (`git tag v1.0.0`): тогда в паспорте отчёта будет указана точная версия агента.

## Советы

* Входной PDF должен содержать текстовый слой (сканы без OCR не поддерживаются). Если есть `.docx` или `.md`-версия документа, точность разбора таблиц будет выше.
* Если не хватает бесплатной квоты, увеличьте `LLM_MIN_INTERVAL` или переключитесь на `gemini-3.1-flash-lite`.
* Для более глубокого анализа подойдут `--model gemini-pro-latest` и `--batch-size 3`.
